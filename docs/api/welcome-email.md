# Welcome email contract

TASK-103 implements the `welcome.activated` event defined by DEC-06.

## Activation boundary

The authenticated dashboard layout verifies the Supabase user server-side, then asks a service-role-only database function to claim the welcome delivery. Invitation links generated by user management return through the localized auth callback using a one-time token hash, so accepted invitations establish the server session before dashboard activation.

The claim is atomic and unique by both member and `welcome.activated:{userId}:v1`. Later sign-ins, restored accounts, role changes, concurrent dashboard requests, and repeated callbacks cannot claim a second delivery.

## Locale and content

`users.preferred_locale` stores `en` or `es`. New invitations seed it from the Administrator's active locale. If it is absent, first activation stores the localized sign-in route. English is the fallback for invalid or missing input.

Both templates include:

- Localized verified role labels
- The localized First Steps guide
- The persistent checklist link for Trainees
- The DEC-02 certification sequence and non-automatic approval warning
- Private-by-default profile and workflow-data guidance
- The localized welcome/support guide and Administrator support path

## Delivery status

`welcome_email_deliveries` stores the safe event snapshot, attempt count, provider message identifier, status, and normalized failure information. Provider response bodies, authentication links, tokens, and workflow private data are never stored or logged.

The statuses implemented by this slice are:

- `sending`
- `provider_accepted`
- `retry_scheduled`
- `failed_permanent`

Retryable failures may be reclaimed on a later authenticated dashboard request after 1 minute, 5 minutes, 30 minutes, 2 hours, and 12 hours, up to six total attempts. TASK-502 will replace this request-driven retry with the reusable delivery worker and verified delivery webhook.

## Authorization

- The browser cannot execute the claim or result-recording functions.
- The server derives the target user from `auth.getUser()` and never accepts a target from request input.
- Members may read only their own welcome-delivery record.
- Administrators may read delivery records for operational support.
- Only the service role may mutate delivery state.
